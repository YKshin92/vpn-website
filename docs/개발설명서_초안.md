## 1. 개발 목적

중국에 거주하는 한국인을 주 고객으로 하는 VPN 서비스의 신청, 결제 확인, 개인별 접속 키 제공, 이용기간 관리와 서버 장애 대응을 웹에서 처리한다.

운영자가 업무 중에도 최소한의 조작으로 고객과 서버를 관리할 수 있도록 한다. 초기에는 관리자가 확인하고 실행하는 방식으로 시작하고, 검증 후 자동화를 확대한다.

### 성공 기준

- 고객은 자신의 이용권, 키, 만료일을 확인할 수 있다.
- 결제 확인 후 한 주문에 이용권이 한 번만 지급된다.
- 서로 다른 고객이 같은 키를 공유하지 않는다.
- 서버 IP 변경 전 계획과 영향 범위를 확인하고 변경 결과와 복구 이력을 추적할 수 있다.
- 운영자 개입이 필요한 실패는 관리 화면에 명확히 표시된다.

## 3. 개발 범위와 우선순위

### 선행 단계: 로컬 DB와 이전 가능한 개발 환경

작업 4 업데이트: 원본 보존 상태로 별도 로컬 DB에 백업 복원하여 데이터·제약·앱 권한·연결 설정을 검증했다. 실제 다른 서버 이전은 미실행이다. 상세는 [DB 백업복원 검증 기록](DB백업복원_검증기록.md)을 따른다. 아래 작업 3 및 이전 단계 설명은 당시 범위의 기록이다.

작업 3 업데이트: 가상 서버·고객·개별 키 테이블과 로컬 저장조회 API, 스키마 적용 이력, 사전 백업을 구현했다. 실제 DB 통합 검사·프로세스 재실행·마이그레이션 재적용 검증을 통과했다. 홈페이지 API 연결과 복원 검증은 미완료다. 상세는 [로컬 백엔드 개발 및 검증](로컬백엔드_개발및검증.md)을 따른다.

로컬에 DB를 설치하고 백엔드에서 연동한다. DB 구조 변경 이력, 가상 데이터, 백업·복원 절차를 관리하여 추후 서버로 이전할 수 있게 한다. 2026-10-16 별도 승인으로 PostgreSQL 17.11 Windows 직접 설치와 개발 DB·앱 계정 생성, 접속·재시작 검증을 완료했다. 로컬 가상 백엔드·업무 테이블은 작업 3, 별도 DB 복원은 작업 4, 관리자 인증·신규 IP 유지 가상 흐름은 작업 5에서 완료했다.

### 1차: 관리자 인증과 서버 IP 수동 변경

홈페이지 디자인은 유지하고, 관리자 로그인·서버 구성 조회·IP 교체 작업 실행·작업 이력·원복 기능을 연결한다. 실제 고객 결제와 신규 키 자동 발급은 다음 단계로 분리한다.

1차 완료 기준: 신규 IP 할당 → 연결 → 서비스 확인 → DNS 갱신 → 검증을 거쳐 새 IP를 유지하고 각 단계가 DB에 기록된다. 기존 고객 키는 유지한다. DNS 변경이 포함되는 실제 실행은 대상과 범위를 설명하고 별도 승인 후 진행한다.

작업 5에서 인증된 관리자 화면과 가상 로직을 새 IP·DNS 유지 흐름으로 수정했다. 부분 실패 시 자동 원복 없이 확인 대기로 중단하고, 명시적 가상 확인 후 현재 신규 IP에 DNS를 맞춰 완료한다. DB에 상태·작업자를 기록한다. 상세는 [관리자 인증·가상 IP 관리](관리자인증_가상IP관리.md)를 따른다.

### 2차: 고객·키·이용기간 관리

고객별 기존 키 연결, 기간 연장, 수동 수납 확인, 만료 처리, 관리 이력을 구현한다. 기존 키를 다시 발급하지 않고 이전할 수 있어야 한다.

### 3차: 고객 신청과 결제 자동화

로그인, 주문, 결제 서버 검증, 키 발급, 마이페이지, 무료체험, 알림을 연결한다.

### 후속 검토

## 6. IP 교체 작업 명세

### 6.1 기본 흐름: 신규 IP로 변경 후 유지

정상 완료 시 기존 IP로 돌아가지 않는다. IP 할당, 인스턴스 연결, IP 반환을 구분하고 반환한 기존 IP를 다시 확보할 수 있다고 가정하지 않는다. 기존 IP가 아직 보유 중이면 재연결 가능한지는 실제 상태를 확인하여 복구 계획으로 검토한다. 아래는 실제 연동의 목표 설계이며 현재 관리 화면은 이를 외부 호출 없이 가상으로 실행한다.

1. 계정·리전·인스턴스·현재 고정 IP·진행 중인 작업 확인
2. 기존 IP와 구성 정보를 복구 자료로 저장
3. 신규 고정 IP 한 개 할당, 작업 결과 확인
4. 기존 IP 연결 해제 후 신규 IP 연결, AWS 완료 상태 확인
5. 신규 IP에 대한 네트워크·서비스 검사
6. 권한 있는 DNS의 대상 A 레코드를 신규 IP로 갱신하고 결과 확인
7. DNS 응답과 기존 도메인·동일 키를 사용하는 실제 Outline Client 재접속 확인
8. 신규 IP를 유지한 상태로 완료하고 기존 IP 보유·반환 여부와 후속 정리 필요 사항 기록

도메인 기반 키를 유지하려면 DNS가 새 IP를 가리키도록 처리해야 한다. IP 연결과 DNS 갱신 사이에는 도메인 접속이 실패할 수 있으며, 이를 신규 IP 불량으로 즉시 판정하지 않는다. DNS 변경이 승인되지 않은 IP 단독 시험은 도메인 접속 복구 완료와 구분하고 별도 계획으로 진행한다.

신규 IP의 실제 VPN 동작은 해당 IP를 대상으로 하는 별도 접속 검증이 필요하다. TCP 연결 성공은 VPN 통신 성공과 구분한다. 기존 고객 키를 수정하지 않는 검증 방법은 별도 시험 클라이언트 또는 테스트 전용 키로 설계한다.

실패 시 실제 IP 보유·연결 상태와 DNS 상태부터 확인한다. 기존 IP가 보유 중이고 재연결을 검증한 경우에만 그 복구 경로를 사용한다. 반환된 IP 재확보나 무조건적인 원복 성공은 전제하지 않는다. 상태가 불명확하거나 복구에 실패하면 추가 IP 할당을 반복하지 않고 관리자 확인 필요로 중단한다. 미연결 IP는 정리 대상으로 표시하고 별도 승인 후 반환한다.

### 6.2 DNS 검증과 기존 IP 정리

기본 변경 흐름에 포함한다. 신규 IP 연결 완료 → 신규 IP 서비스 검사 → 권한 있는 DNS의 대상 A 레코드 갱신 → DNS 응답과 실제 클라이언트 검증 순서로 진행한다.

- TTL 경과만으로 모든 고객의 DNS 캐시 갱신을 보장하지 않음
- AAAA·다른 레코드·외부 DNS 설정의 영향도 사전 확인
- 실패 시 보유 중인 IP와 실제 DNS 상태에 따라 복구 계획을 선택하고 실행 가능 여부 확인
- 기존 IP 반환 시점은 별도 정책으로 정하고 초기에는 보존
- 변경 후에도 Outline 키의 도메인·포트·암호는 유지

`[결정 필요]` 검사 시간 제한, 재시도 횟수, 기존 IP 보관기간·반환 승인 방식, 신규 IP 정리 정책

### 작업 상태 제안

`요청됨 → 사전 점검 → IP 확보 → 연결 변경 → 서비스 검사 → DNS 갱신 → 접속 검증 → 신규 IP 유지·완료`

## 7. 고객·결제·키 정책

### 7.1 고객과 키 관계

- 서로 다른 고객에게 동일한 키를 할당하지 않는다.
- 고객이 사용하는 기기 수와 키 수는 별도 정책으로 확정한다.
- 1차 제안: 한 고객에 활성 키 하나, 재발급과 이전 키 이력은 별도 보관
- 기간 연장은 가능한 한 기존 키를 유지
- 기존 고객 이전 시 미연결·중복·분실 키는 담당자가 검토

`[결정 필요]` 여러 기기 허용 여부, 고객별 키 수, 트래픽 제한, 서버 이동 시 처리

### 7.2 이용권과 무료체험

- 화면의 30일 12,000원 / 90일 30,000원 / 180일 54,000원은 현재 예시 가격
- 제안: 유효기간 중 연장은 기존 만료일, 만료 후 구매는 결제 검증 완료 시각부터 계산
- 무료체험은 24시간, 자동 유료 전환 없음
- 이메일 주소만으로 동일인 중복 체험을 완전히 방지할 수 없으므로 본인 확인·신청 제한 정책 필요
- 시간은 DB에서 UTC로 저장하고 고객 화면은 한국시간 등 정한 기준으로 표시

`[결정 필요]` 최종 가격, 이용 시작 기준, 무료체험 확인 방식, 데이터 한도, 만료 유예기간

### 7.3 결제 및 지급

1. 서버에서 상품 가격과 주문을 확정
2. 선택한 결제 수단으로 결제
3. 서버에서 결제 제공자의 결과와 금액·통화·주문 ID 검증
4. 동일 결제·주문 중복 처리 방지
5. 이용권 반영 및 키 발급 작업 예약
6. 실제 키 발급 성공 후 고객 화면에서 제공

결제 성공 후 키 발급 실패는 ‘결제 완료·발급 대기’로 기록하고 재시도한다. 재시도 전에 해당 고객 키가 이미 생성됐는지 확인하여 중복 발급을 방지한다. 고객 화면의 결제 성공 표시만으로 키를 지급하지 않는다.

환불·결제 취소·분쟁 발생 시 이용권 조정과 키 사용 중지 정책을 연결한다. 최초에는 수동 수납 확인으로 시작할 수 있다.

`[결정 필요]` PG, 사용 가능한 결제 수단, VPN 상품 취급 가능 여부, 통화, 환불·부분 환불·장애 보상 정책

### 7.4 만료 처리

만료 시간을 주기적으로 검사하고 실제 서버 접근 제한을 적용한다. 웹사이트의 상태를 ‘만료’로 바꾸는 것만으로 VPN 접속을 차단할 수는 없다. Outline에서 사용할 제한·삭제·재발급 방식을 먼저 검증하고, 기간 연장과 만료 처리가 동시에 실행될 때 최신 이용기간을 재확인한다.

`[결정 필요]` 만료 키 유지·회수 방식, 재구매 시 키 재발급 허용 여부

### 8.1 로컬 DB와 서버 이전 준비

환경 확인 후 PostgreSQL 17.11을 Windows에 직접 설치했다. 127.0.0.1:5432의 개발 DB와 제한된 앱 계정, 수동 시작 서비스가 구성되었다. 비밀번호는 브라우저나 저장소에 넣지 않고 Windows 암호화 방식의 로컬 파일로 보관한다. Node.js v24.18.0·npm 11.16.0은 기존 설치를 활용하며 로컬 가상 백엔드는 후속 작업 3에서 구현·검증했다. 적용 값과 검증은 [로컬 DB 설치 및 운영 기록](로컬DB_설치및운영.md), 초기 제안은 [로컬 개발 환경 구성안](로컬개발환경_구성안.md)을 따른다.

- 로컬 DB 설치와 백엔드 연동을 먼저 진행하고 운영 서버로의 이전은 별도 단계로 둔다.
- 로컬 DB는 PostgreSQL 17.11 Windows 직접 설치로 적용했다. 포트·데이터 경로 등 변경 시 별도 계획과 승인을 거친다.
- DB 접근은 백엔드만 담당하며 프런트엔드에 연결 문자열과 비밀번호를 포함하지 않는다.
- 연결 주소·포트·DB명·사용자·비밀번호는 환경별 설정으로 분리한다. 저장소에는 값 없는 설정 예시만 둔다.
- 스키마 변경은 번호가 있는 마이그레이션 파일로 관리한다. 실행 전 대상·데이터 영향·복구 방법을 설명하고 승인받는다.
- 초기 데이터는 가상 고객과 개별 가상 키만 사용한다. 실제 고객 데이터 이전은 별도 승인 대상이다.
- 로컬 데이터·DB 덤프·비밀번호·실제 키를 버전 관리에서 제외한다.
- 이전할 서버에서도 호환 가능한 DB 환경을 구성하고 스키마·확장·인코딩·시간대 차이를 확인한다.
- 이전 절차: 원본 백업 → 별도 DB 복원 연습 → 건수·제약·관계 검증 → 승인된 전환 시점에 쓰기 중지 또는 동기화 → 최종 백업·복원 → 백엔드 설정 전환 → 기능 검수.
- 전환 후 쓰기가 발생하면 단순히 옛 DB로 연결을 되돌릴 경우 데이터가 유실될 수 있으므로 복구 시 데이터 반영 방법까지 정한다.
- 완료 기준: 로컬 저장 데이터가 재시작 후 유지되고, 새 빈 DB에 마이그레이션 적용 및 백업 복원이 가능하며, 연결 설정만 변경해 백엔드가 동작한다.

`[결정 필요]` 백엔드 세부 구성·호스팅 위치, 서버 이전 시 DB 버전·설치 방식, 월 예산, 별도 관리 서버 사용 여부

## 10. 백엔드 API 초안

아래 경로는 제안이며 실제 구현 경로가 아니다. 모든 관리자 요청은 인증·권한 검사, 입력 검증, 감사 기록을 거친다.

| API 예시 | 목적 |
| --- | --- |
| `GET /api/admin/servers` | 서버 목록 조회 |
| `GET /api/admin/servers/:id` | 실제 구성과 최근 조회 결과 |
| `POST /api/admin/servers/:id/ip-change-plans` | 변경 계획 생성 및 사전 점검 |
| `POST /api/admin/ip-change-plans/:id/execute` | 유효한 계획 실행, 중복 방지 ID 필수 |
| `GET /api/admin/jobs/:id` | 진행 상태·단계별 이력 조회 |
| `POST /api/admin/jobs/:id/rollback` | 복구 가능한 작업 원복 요청 |
| `GET /api/admin/customers` | 고객 검색·필터 |
| `POST /api/admin/customers/:id/extensions` | 기간 연장과 사유 기록 |
| `GET /api/me/pass` | 로그인 고객 본인의 이용권 |
| `POST /api/orders` | 서버 기준 주문 생성 |
| `POST /api/payments/webhook` | 제공자 검증 후 결제 반영 |

실행 응답은 장시간 연결을 유지하기보다 작업 ID를 반환하고 화면이 상태를 조회하는 방식을 제안한다. 오래된 계획·이미 완료한 작업·다른 서버의 작업 요청은 거절한다.

## 11. 보안·운영 요구사항

- AWS 권한은 확정된 서버 작업과 DNS 범위에 필요한 최소 범위로 구성
- 브라우저에서 AWS 키나 Outline 관리 URL을 입력·보관·노출하지 않음
- 관리자 로그인·실행 요청에 요청 위조 방지, 요청 제한, 세션 보호 적용
- 키·인증정보·전체 결제 응답이 로그나 오류 메시지에 남지 않도록 제거
- 실제 결제정보는 PG의 처리 방식을 이용하고 카드번호를 직접 저장하지 않음
- 작업 실패 알림에 비밀정보를 포함하지 않음
- DB 백업과 복원 절차 검증
- 개인정보 처리방침, 이용약관, 결제 규정, 서비스 제공 지역 관련 법적 요건 별도 검토

알림 제안: IP 변경 완료, 복구 실패, 결제 완료 후 발급 지연, 만료 처리 실패 시 운영자에게 통지한다. 정상 상태가 유지되는 동안 반복 알림은 보내지 않는다.

## 15. 실제 운영 변경 승인 경계

문서 작성·코드 개발·가상 테스트는 현재 개발 범위다. 이 문서는 실제 AWS 변경·DNS 수정·기존 키 삭제·운영 DB 마이그레이션·결제 실행을 승인하는 문서가 아니다.

이전에 승인된 IP 교체 후 원복 테스트는 수행되지 않았고 이후 요구사항이 변경되었다. 이전 승인을 신규 IP 유지·DNS 갱신 작업의 승인으로 확대 해석하지 않는다. 실제 작업 전 변경된 대상·절차·비용·영향·실패 대응을 다시 설명하고 최종 승인을 받는다.

## 16. 작업 진행·문서·GitHub 원칙

1. 작업 전에 목적, 수정 파일·구성, 검증 방법, 영향과 이번에 하지 않을 범위를 설명한다.
2. 사용자의 최종 승인 후 해당 범위만 실행한다. 추가 설치·삭제·외부 변경 등 범위가 커지면 먼저 설명하고 다시 승인받는다.
3. 완료 후 실제 완료·미완료·검증 결과·한계를 보고하고 [작업 현황](작업현황.md)에 기록한다. 관련 명세 변경은 이 문서에도 반영한다.
4. 완료 판단을 화면 구현 / 로컬 가상 검증 / 실제 연동 검증 / 배포로 구분한다. 실행하지 않은 작업은 완료로 표시하지 않는다.
5. 다음 작업과 승인받을 범위를 안내하고 승인 전 실행하지 않는다. 이전 단계의 승인은 후속 단계의 포괄 승인이 아니다.
6. GitHub 커밋·푸시·PR·배포는 사용자가 별도로 요청한 경우에만 한다. 기본 작업 결과는 로컬에 둔다.
7. 작업 문서와 저장소에는 실제 고객정보·키 원문·비밀번호·관리 API 비밀 주소를 기록하지 않는다.

### 변경 이력

최신 요구는 [고객관리·기간·결제·매출](고객관리_기간결제매출.md)과 [실제 IP 승인 경로](실제IP변경_승인계획.md)를 따른다. 상위 메뉴는 고객관리·서버관리 두 개다. 실제 변경 경로와 전용 live 테이블을 연결했으나 서버 측 게이트는 비활성으로 유지했고 조회·계획 저장만 했다. 고객 장부는 .test 가상 데이터 전용이며 실제 결제·Outline 키와 연동하지 않았다. 아래 작업 7의 미연결 문구는 당시 기록이다.

작업 7의 상태·감사 기록과 검증은 [IP 변경 작업 실행기](IP변경_작업실행기.md)를 따른다. 작업 DB·HTTP는 mock만 허용하고 실제 SDK 변경 어댑터는 기본 비활성이며 라우트와 분리했다. 각 단계의 intent를 먼저 저장하고 실패·중단 시 확인 대기로 멈춘다. 여러 서버 조회는 최대 10개의 서울 서버별 도메인 설정과 목록/선택 상세를 지원한다. 실제 운영 변경 승인·live 저장 경로·실행 진입점은 후속 연결이 필요하다.

작업 6의 구체 구현·권한·검증·미확인 사항은 [AWS·DNS 읽기 전용 연동](AWS_DNS_읽기전용_연동.md)에 기록했다. 사용자 콘솔 임시 인증과 기대 계정 확인 후 서울 서버·글로벌 DNS 영역·공개 DNS를 실제 관리자 HTTP API로 조회·대조했다. IP·DNS 변경은 구현·실행하지 않았다.
