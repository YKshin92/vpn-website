# DB 백업·복원 검증 기록

2026-10-16 / 작업 4 완료 / 로컬 가상 데이터 대상

## 실행 범위

사용자가 승인한 백업·복원 연습을 수행했다. 원본 `ieum_vpn_dev`를 읽기 전용 일관성 스냅샷으로 백업하고, 새 `ieum_vpn_restore_test`에 복원했다. 원본을 덮어쓰거나 기존 DB를 삭제하지 않았다. 실행 중인 API의 DB 연결도 변경하지 않았다. GitHub·AWS·DNS·Outline·결제에는 반영하지 않았다.

## 관계·제약·접속 검증

- 고객이나 서버를 잃은 키 매핑 0개.
- 서로 다른 고객에게 같은 서버의 동일 키를 할당하면 고유 제약 오류로 거부.
- 이미 키가 있는 고객에게 두 번째 키를 할당하면 거부.
- 존재하지 않는 고객을 참조하는 키는 외래키 오류로 거부.
- 앱 계정의 CREATE TABLE 시도 거부.
- 시험 변경은 복원 DB의 트랜잭션 안에서 수행하고 항상 ROLLBACK. 검사 후 복원 데이터 해시 불변 확인.
- 원본 데이터와 스키마도 작업 전후 동일함을 확인.
- 복원 DB의 PUBLIC 접근을 회수하고 기존 앱 계정에 CONNECT를 부여. DB·업무 스키마 생성 권한은 없음.
- 백엔드 연결 설정 PGDATABASE를 복원 DB로 지정한 별도 테스트 프로세스에서 현재 DB명과 같은 고객·서버·키 조회 API 동작 확인.
- TypeScript 빌드, 복원 API 검사 1개, 원본 DB 통합 검사 Node 집계 10개 통과.

## 보관 위치

현재 사용자·SYSTEM·Administrators로 접근을 제한한 기존 로컬 전용 폴더에 보관한다. 비밀번호·행 원문은 결과 문서에 기록하지 않는다.

백업:
`C:\Users\sesal\AppData\Local\IeumVPN\postgres-local\backups\restore-rehearsal-2026-10-15T15-32-46-817Z.dump`

검증 결과:
`C:\Users\sesal\AppData\Local\IeumVPN\postgres-local\restore-result-2026-10-15T15-32-46-817Z.json`

파일명 시각은 UTC 식별자다. 한국시간 2026-10-16에 실행했다. 시험 DB는 삭제하지 않고 남겨 두었다. 데이터 경로를 복사하는 방식이 아니라 pg_dump·pg_restore를 사용했다.

## 재현·연결 설정

`tools/verify-db-restore.ps1`은 보호된 Windows 자격증명을 프로세스 환경에 주입하고 `tools/verify-db-restore.mjs`를 실행한다. 이 명령은 백업 생성·시험 DB 생성·복원까지 수행하므로 향후에도 승인 범위에서만 실행한다. 시험 DB가 이미 있으면 덮어쓰지 않고 중단하며 자동 삭제·강제 재생성 옵션은 없다. 실패해도 시험 DB를 자동 삭제하지 않으므로 상태 확인 후 별도 처리한다.

`tools/test-restored-api.ps1`은 이미 복원된 DB의 조회와 앱 권한만 검사한다.

백엔드는 환경설정으로 `ieum_vpn_dev` 또는 `ieum_vpn_restore_test`만 허용한다. Windows 실행 도구의 기본 DB는 원본이며, 시험 DB를 지정하려면 다음과 같이 실행할 수 있다. 기존 3000 API가 실행 중이면 같은 포트에서 동시에 실행하지 않는다. 이번에는 별도 테스트 프로세스에서만 연결 설정을 검증했고 기존 API를 전환하지 않았다.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/backend.ps1 -Task start -Database ieum_vpn_restore_test
```

`-Task migrate`와 `-Task seed`는 원본 개발 DB만 허용하고 복원 DB 대상으로는 거부한다. 비밀번호는 로그·명령 인자에 출력하지 않고 실행 후 프로세스 환경을 원상 복구한다.

## 실제 서버 이전 전 남은 사항

이번 시험은 같은 Windows PC·동일 PostgreSQL 클러스터에서 수행했다. Linux/AWS 서버·다른 메이저 버전으로의 실제 이전 성공을 의미하지 않는다.

- 다른 서버에는 postgres·ieum_app 등 역할과 비밀정보를 별도로 구성해야 한다. DB 백업만으로 전역 역할·비밀번호가 이전되는 것은 아니다.
- 이번 복원은 --no-owner로 기존 로컬 관리 계정이 소유하도록 했다. 실제 서버의 소유자·마이그레이션 계정·앱 권한을 별도 확정해야 한다.
- Windows 암호화 자격증명 파일을 서버에 복사하지 않고 서버 비밀 저장소 또는 환경변수를 새로 설정한다.
- 파일 전송·보관 암호화·접근권한·백업 주기·보관기간·복구 목표를 확정해야 한다.
- 운영 쓰기 중지·최종 백업·전환·검수·전환 후 새 데이터 보존을 포함한 실패 복구 계획을 승인받아야 한다.
- 현재 두 개발 DB로 제한한 설정은 운영 배포 설계 시 재검토한다.

다음 단계는 관리자 인증과 신규 IP 유지 방식의 가상 관리 흐름이다. 별도 계획 설명·사용자 승인 후 진행한다.
