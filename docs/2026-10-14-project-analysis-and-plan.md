## 2. 보안·운영상 발견 사항

1. 데모 제출은 서버 결제 검증 없이 이용권을 표시한다. 현재 데모임을 명시하므로 실제 결제 취약점이 발생한 것은 아니지만 실서비스로 사용할 수 없다.
2. 만료일이 클라이언트 시간에 의존하고 영속성이 없다. 운영에서는 서버 UTC 시각과 DB 트랜잭션으로 계산해야 한다.
3. preview.cjs의 decodeURIComponent 예외가 처리되지 않는다. 잘못 인코딩된 요청으로 프로세스가 종료될 수 있다. 로컬 미리보기 전용이며 운영 웹서버로 사용하지 않는다.
4. 패키징 파일과 .site-stage가 Git 미추적 상태로 남아 있고 .gitignore가 없다. 향후 .env, 자격증명, DB 덤프, 키 내보내기, 로그와 배포 부산물의 제외 규칙부터 추가한다. 현재 검사한 소스에서는 실제 자격증명을 발견하지 않았다. 계정 전체 비밀정보 감사 결과는 아니다.
5. 관리 API, 인증, 접근 제어 자체가 없으므로 관리자 보안이 갖춰졌다고 평가할 수 없다.
6. 기존 문서는 과거 '서비스 종료'와 동적 키 전환을 전제로 한다. 최신 요구의 '운영 중, 도메인 기반 ss:// 키 유지'를 설계 기준으로 삼는다. 과거 기록을 자동 수정하지 않았다.
7. 종교적 소속을 고객 DB 필수 항목으로 추가하지 않는다. 서비스 운영에 필요한 최소 연락처·이용권 정보만 설계한다.

## 4. 아키텍처 제안

기존 정적 고객 사이트를 유지하며 별도 서버 측 시스템을 추가한다. JavaScript 자산과의 일관성을 위해 신규 백엔드는 TypeScript/Node를 우선 후보로 하고, DB는 관계·거래·감사 이력을 위한 PostgreSQL을 제안한다. 아직 설치·프로비저닝하지 않는다.

```text
고객 사이트 / 관리자 화면
             │ 인증된 HTTPS
             ▼
고객·이용권 API ── PostgreSQL (고객, 주문, 결제, 기간, 감사, 작업 큐)
             │
             └─ Outline 작업자 ── 서버별 관리 API

관리자 수동 CLI ── IP 교체 작업자 ── Lightsail API
                     │            └─ DNS 공급자 API
                     └─ 독립 작업 상태 저장소·잠금·감사 로그
```

IP 작업자는 고객 서비스 장애와 독립적으로 실행한다. 웹 요청 수명 안에서 IP 교체를 끝내려 하지 않는다. CLI가 작업을 생성하고 작업자가 단계별 상태를 저장한다. 초기 단일 실행 호스트의 잠금과 저널을 구현하고, 다중 호스트 지원 전 공유 잠금·lease·fencing을 도입한다. CLI와 자동 작업을 별도로 만들어 중복 실행시키지 않고 같은 잠금 경로를 사용한다.

역할은 관리자, 마케팅 담당자, 고객으로 분리한다. 마케팅 담당자는 고객·수납 확인 권한만 갖고 AWS 및 관리 API 비밀을 받지 않는다. IP 작업자는 별도 최소 권한 AWS 자격증명을 사용한다. 사이트 정적 배포 계정과 운영 인프라 변경 권한도 분리한다.

제안 소스 구조: 기존 dist 보존, services/control-api, services/outline-worker, tools/ip-rotation, packages/domain, tests/fixtures, docs. 아직 생성하지 않은 계획 구조다.

## 5. Lightsail IP 교체 설계

### 핵심 결정

- 기존 IP를 먼저 반환하지 않는다. 새 IP 확보 여유가 없으면 안전하게 중단한다.
- 도메인 기반 ss:// 키는 유지한다. 도메인이 새 IP로 해석되고 기존 포트·암호·암호화 방식이 유지돼야 같은 키로 연결할 수 있다.
- 동적 접속 키로의 전환은 필수 조건이 아니다. 현재 도메인과 DNS 갱신 경로 확인이 우선이다.
- IP를 바꿔도 중국에서 접속된다는 보장은 없다. 인프라 완료와 중국 검증 상태를 별도로 기록한다.
- 실행 계획은 기본 dry-run. 실제 apply는 운영 승인 후 별도로 활성화한다.

### 상태 전이

1. LOCKED: 계정·리전·인스턴스 단위 잠금, 실행 UUID와 승인된 대상 기록.
2. PREFLIGHT: 인스턴스·기존 IP 연결 관계, 서비스 포트, DNS, 관리 채널, 할당 여유 검증. 예상 상태와 다르면 중단.
3. SNAPSHOT: 기존 IP 이름/주소·DNS 원본/TTL·관련 버전·실행자·시작 시각 저장. 비밀 URL·키·AWS 토큰은 기록하지 않음.
4. ALLOCATE_REQUESTED: 실행 ID 기반 새 IP 이름을 먼저 기록한 후 AllocateStaticIp. 타임아웃이면 조회로 실제 생성 여부를 확인하고 중복 생성하지 않음.
5. ALLOCATED: AWS 작업을 GetOperation으로 조회. HTTP 성공만으로 다음 단계로 진행하지 않음. 성공 상태와 실제 리소스 상태 모두 확인.
6. OLD_DETACHED: 기존 IP DetachStaticIp 후 작업 완료 확인. 기존 IP 소유권은 유지. 이때 임시 동적 공인 IP 및 서비스 중단 가능성을 고려.
7. NEW_ATTACHED: AttachStaticIp 후 GetOperation 및 GetStaticIp/GetInstance의 부착 대상·공인 IP 교차 확인.
8. DNS_UPDATED: DNS 변경 주체가 확정된 경우에만 대상 레코드를 갱신. 원본과 현재 값이 다르면 동시 변경으로 보고 중단. CNAME/AAAA/프록시를 무시하지 않음. 기존 DDNS가 담당한다면 그 변경 완료를 확인하고 중복 갱신하지 않음.
9. VERIFIED: 권한 DNS·복수 리졸버, 포트, 실제 터널, 필요한 관리 API 연결 검증. TTL과 앱 캐시 때문에 즉시 전환을 보장하지 않음. 중국 검사 미확보 시 CHINA_UNVERIFIED로 별도 표시.
10. OLD_RELEASE_PENDING: 정책상 관찰 기간과 검증 조건 충족 후 기존 IP 반환 후보로 표시. 초기 MVP는 별도 관리자 실행으로 반환.
11. COMPLETE: ReleaseStaticIp 완료·실제 반환 상태 확인, 결과 기록, 잠금 해제.

### 실패·재실행

- 분리 전 실패: 기존 서비스 유지, 새 할당 IP만 상태 확인 후 정리 후보로 남김.
- 연결/DNS/검증 실패: 실제 AWS 및 DNS 상태를 다시 읽고 이전 IP 재연결과 DNS 원복을 시도하는 보상 절차. DNS TTL 때문에 원복도 즉시 완료되지 않을 수 있다.
- 요청 타임아웃: 실패라고 단정하거나 다음 단계 실행하지 않고 operation ID·리소스 이름으로 상태 재조정. 상태를 확정할 수 없으면 NEEDS_MANUAL_INTERVENTION.
- 외부 운영자의 DNS 변경이 감지되면 원본으로 무조건 덮어쓰지 않음.
- 프로세스 종료 후 같은 실행 ID로 재개. 성공 처리된 단계도 실제 상태를 대조한다.
- 반환 이후 기존 IP를 다시 확보할 수 있다고 가정하지 않음. 새 복구 계획이 필요하다.
- 롤백은 기술적 변경 원복이다. 이전 IP가 중국에서 이미 차단됐다면 중국 연결 복구를 뜻하지 않는다.

감사 필드: 실행 ID, 실행자, 대상 계정/리전/인스턴스, 이전·신규 IP, 단계, operation ID, DNS 변경 전후 값, 시간, 검사 결과, 오류 분류, 수동 개입 여부. 로그 접근 권한·보관 기간을 제한한다.

## 6. Outline API 연동

공식 README와 OpenAPI 명세를 확인했다. 설치된 운영 서버 버전의 지원 여부는 미확인이다.

| 목적 | 공식 명세 경로 |
| --- | --- |
| 서버 정보 | GET /server |
| 목록·단일 조회 | GET /access-keys, GET /access-keys/{id} |
| 생성 | POST /access-keys |
| 이름 변경 | PUT /access-keys/{id}/name |
| 삭제 | DELETE /access-keys/{id} |
| 키별 제한 설정·해제 | PUT /access-keys/{id}/data-limit, DELETE 동일 경로 |
| 사용량 | GET /metrics/transfer |

읽기 전용 어댑터부터 구현하고 실제 인증서는 보안 경로로 받은 지문 또는 신뢰 설정으로 검증한다. README의 --insecure 예제를 운영 기본값으로 복제하지 않는다. 전체 apiUrl의 비밀 경로, password, accessUrl을 응답 로그·오류 추적·브라우저에 노출하지 않는다. 고객 화면에는 인증된 본인의 접속 키만 제공한다.

관리 URL이 IP를 포함하면 IP 변경 후 URL의 호스트만 검증된 주소로 교체하거나 안정적인 관리 경로를 사용한다. 비밀 경로·포트·인증서 신뢰는 유지하며 실패 시 임의로 TLS 검증을 끄지 않는다.

공식 명세에는 이용 만료일 필드가 없으므로 만료 판정은 고객 시스템에서 수행한다. 키 삭제와 일시정지는 구분한다. 같은 키로 연장 복구가 필요한 정책이라면 삭제를 기본 동작으로 확정하지 않는다. 사용량 제한을 일시정지 기능처럼 쓸 수 있는지도 설치본 검증 없이는 가정하지 않는다.

키 생성 API와 DB는 단일 트랜잭션이 아니다. 발급 작업 ID를 저장하고 서버별 작업을 직렬화하며, 생성 성공/응답 유실 시 재조회·대조한다. POST를 무조건 반복하지 않는다. 미확정 발급은 수동 검토 상태로 남긴다. 데이터 사용량은 관측 시각과 함께 저장하고 재시작·카운터 감소·집계 기간을 확인하기 전 과금 근거로 쓰지 않는다.

## 7. 데이터 모델 제안

| 테이블 | 핵심 필드·제약 |
| --- | --- |
| customers | UUID, 표시명, 최소 연락처, customer_status, import_batch_id; 로그인 없는 기존 고객 허용 |
| identities | customer_id, 인증 제공자 subject 고유값; 교인 여부 수집 안 함 |
| servers | UUID, provider/region/instance, outline_server_id, key_hostname, secret_ref, 상태 |
| access_keys | UUID, server_id, outline_key_id(문자열), 이름, 상태, secret_ref, 관측 시각; UNIQUE(server_id, outline_key_id) |
| customer_key_assignments | customer_id, key_id, 시작·종료 시각, 매핑 근거, 확인자; 공유 여부 확인 전 1:1 강제 안 함 |
| plans | 상품 코드, 기간, 금액(최소 통화 단위 정수), 통화, 정책 버전 |
| orders | 고객, 상품/가격/기간 스냅샷, 상태, 요청 중복방지 키 |
| payments | 주문, 제공자 또는 manual, 제공자 거래 ID 고유 제약, 금액·통화, 상태, 확인자·확인 시각 |
| payment_events | 제공자+이벤트 ID 고유 제약, 검증·처리 상태, 최소 보관 정보 |
| entitlements | 고객, 서비스/서버 범위, 유효 시작·종료(UTC), 상태, hold_reason, 회수 허용 여부 |
| entitlement_events | 부여·연장·보상·환불 조정, 원인 주문/수납, 이전·이후 종료일, 실행자; 동일 원인 중복 적용 금지 |
| provisioning_jobs | 작업 ID, 대상 주문/키, 단계, 시도 횟수, 재조회 상태, 다음 시도 시각 |
| audit_events | 실행자·역할, 행위, 대상, 민감정보 제거 전후값, 시각, 상관 ID |
| import_batches | 원본 참조·해시, 건수, 검증 결과, 상태, 확인자 |

고객 상태, 결제 상태, 이용권 상태, 실제 키 상태를 하나의 status로 합치지 않는다. 키의 존재가 결제 완료를 의미하지 않는다. 키 번호는 서버마다 중복될 수 있다.

연장은 정책 확정 후 `max(현재 유효 종료일, 서버 현재시각) + 구매 기간`을 기본 후보로 한다. 무료 기간·일시정지·부분 환불·정확한 일수/달력일 정의는 별도 결정한다. 만료 작업과 연장 결제는 동일 이용권 잠금/버전 검사를 사용하고, 삭제 직전 재검증한다. 원격 삭제와 DB 변경 사이 경쟁은 작업 상태·보상 처리까지 검증한다.

## 8. 기존 고객 이전

1. Outline 목록과 기존 고객 원장을 읽기 전용으로 수집. 키 원문은 제한된 저장소로만 취급.
2. server_id + outline_key_id 기준으로 inventory를 먼저 등록. 기존 서버 키를 생성·수정·삭제하지 않음.
3. 고객별 이름/연락처/담당자 기록으로 매핑 후보 생성. 이름만 일치하면 확정하지 않음.
4. 공유 키, 중복 고객, 주인 불명 키, 무료 고객, 만료일 불명을 별도 검토 목록으로 분리.
5. 만료일 불명은 NULL + review_required + 자동회수 제외. 임의 날짜나 '현재 만료'로 변환하지 않음.
6. 건수·서버별 키 수·고객 매핑·샘플 비교 후 담당자가 확인.
7. 별도 staging DB에서 승인된 마이그레이션과 import를 먼저 시험. 이번 작업에서는 DB 생성/마이그레이션도 실행하지 않음.
8. 운영 import 승인 후 적용하되 자동 만료 작업은 비활성. 관찰 기간 후 정책과 대상별 회수 권한을 별도로 승인.

원장 입력을 바꿔 재수입해도 중복 고객·키를 생성하지 않도록 배치 식별과 원본 ID 매핑을 유지한다. 복구는 새 관리 데이터의 매핑을 되돌리는 방식으로 하고 원래 키를 지우지 않는다.

## 9. MVP·순서·의존성

| 순서 | 개발 범위 | 완료 기준 / 의존성 |
| --- | --- | --- |
| 0 | 설정 모델, 비밀정보 제외, 인프라 확인표 | 계정·리전·호스트·DNS·키 현황 명확화 |
| 1A | IP 교체 계획기와 가짜 AWS/DNS 어댑터 | 운영 호출 없이 상태 전이·오류·재개 시험 |
| 1B | Outline 읽기 전용 어댑터와 키 인벤토리 | 인증서 검증·마스킹·버전 차이 처리 |
| 2A | 관리자 수동 IP 교체 CLI | DNS 경로 확정, 별도 시험 서버 검증, 운영 승인 필요 |
| 2B | 관리자 인증·고객·키 매핑·수납·기간 관리 | DB 스키마 승인, staging 검증, 기존 키 보존 |
| 3 | 발급·만료 후보 목록·감사·알림 | 첫 MVP는 만료 후보를 사람이 확인, 자동 삭제 제외 |
| 4 | 고객 로그인·마이페이지·PG 테스트 | PG/정책 선정, 계정 권한 검증, 중복 웹훅 처리 |
| 5 | 운영 결제·자동 발급·자동 만료 | 운영 승인 및 전체 시나리오 통과 |
| 후속 | 중국 장애 감지 기반 자동 IP 전환 | 충분한 현지 측정·오탐 기준·비용 통제 확보 |

1A와 1B는 독립 모듈이다. 초기 MVP에 PG를 필수로 묶지 않고 담당자의 수동 수납 확인부터 DB에 기록한다. 자동 정기결제, 다국어, 자동 중국 차단 판정은 초기 범위에서 제외한다.

## 10. 테스트와 배포 전략

이번 로컬 검사: `node --check dist/app.js`, `node --check preview.cjs` 통과. 기능·브라우저 E2E·운영 연결 검증을 의미하지 않는다.

새 코드의 로컬 테스트는 가짜 어댑터로 아래를 검증한다.

- AWS 실패·타임아웃·응답 유실·늦은 완료 시 단계 진행 금지, 기존 IP 조기 반환 금지.
- DNS 미확인, A 불일치, 외부 변경, TTL 지연, 복구 실패 시 안전한 중단.
- 중복 실행, 프로세스 종료, 잠금 만료 후 재개, 오래된 작업자의 후속 변경 차단.
- Outline 인증서 불일치·비밀정보 마스킹·키 생성 응답 유실·404/버전 차이.
- 중복 수납/웹훅·금액 불일치·동시 연장·만료 경쟁·환불 후 키 상태.
- import 재실행·동명이인·공유 키·만료일 불명에서 기존 키 무변경.
- 인증되지 않은 요청과 다른 고객 키 조회 차단, 관리자 역할별 권한.

시험 서버/도메인/DB에서 통합 테스트 → 운영 읽기 전용 대조 → 담당자 제한 사용 → 승인된 작은 범위의 운영 쓰기 순서로 배포한다. 시험 리소스 생성도 비용이 드는 AWS 변경이므로 사전 승인이 필요하다. 운영 키 발급·변경·삭제, DNS 수정, DB 마이그레이션, 결제는 명시적 승인 후만 수행한다.

## 11. 다음 개발 착수점

우선 네트워크 호출이 없는 IP 교체 계획기·상태 전이 테스트와 설정 검증부터 작성한다. 실제 AWS 실행 어댑터는 확인된 계정/리전/DNS 범위에 맞춰 연결한다. 이번 턴은 요청대로 실제 분석 결과와 구현 계획을 먼저 보고하며 운영 실행 코드를 연결하지 않았다.

우선 필요한 비밀이 아닌 정보: AWS 리전·인스턴스명, 액세스 키의 도메인과 포트(전체 키 제외), DNS 관리 업체, 대략적 고객·키 수 및 공유 키 여부. API URL/비밀번호/AWS 키는 대화에 붙이지 않고 이후 서버 측 비밀 저장소 설정으로 전달한다.
