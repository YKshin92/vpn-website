# 서버별 Outline 키 관리 확장 계획

2026-10-17 초안 · 2026-10-18 구현 승인 후 조회/제어 코드·모의 검증 완료, DB 적용·영속/복원 검증 완료, 전용 키 실제 생성/이름/한도/삭제 시험 완료, 운영 상시 쓰기는 비활성

현재 구현 결과는 [서버별 키 관리 구현](서버별_키관리_구현.md)을 기준으로 한다. 아래는 최초 계획이며 사용량 시계열·고객 매핑 등 후속 항목을 포함한다.

## 현재 확인

사용자가 현재 관리 연결 정보 저장 후 실제 키 목록 조회 성공을 확인했다. 다음 요구는 서버별 키 현황, 생성·활성화 날짜, 사용량·기기 관련 정보, 생성·삭제 기능이다. 이 문서는 설계이며 실제 키 변경이나 DB 마이그레이션을 실행하지 않는다.

## 화면

서버 상세의 키 탭에서 넓은 키 관리 화면으로 이동한다. 서버 선택·검색·고객 연결 여부 필터, 최근 동기화 시각과 오류 상태를 제공한다. 상단에 현재 키 수·고객 연결/미연결 수·집계 가능한 사용량을 표시한다. 기본 목록은 키 ID·이름·연결 고객·사용량/한도·이용 상태로 구성하고 날짜와 운영 이력은 우측 상세에 표시한다. 삭제 기록은 현재 목록과 분리한다.

## 정보 정의와 한계

| 항목 | 처리 |
| --- | --- |
| 키 ID·이름·포트 | 현재 Outline 조회 확장 |
| 생성일 | 이 시스템에서 생성 성공을 확인한 시각. 기존 키의 원래 생성일은 확인 불가로 표시 |
| 최초 등록/발견일 | DB에서 별도 보관. 기존 키 생성일로 표시하지 않음 |
| 이용 시작·만료일 | 고객 구독/관리자 지정 운영 데이터. 키 생성·활성화나 실제 연결과 구분 |
| 최초 사용 감지일 | 수집을 시작한 이후 처음 트래픽을 감지한 시각. 과거 최초 사용일로 소급하지 않음 |
| 최근 사용 시각 | 서버가 제공하는 실험적 지표가 지원되는 경우 표시. 조회 불가와 미사용을 구분 |
| 사용량·한도 | 전송량 API와 개별/서버 기본 한도를 구분. API가 제공하는 집계 범위를 명시하고 월별이라고 추정하지 않음. 리셋/재설치로 값 감소 시 불연속을 기록 |
| 최대 관측 기기 수 | 실험적 metrics가 지원될 때 조회 범위와 함께 표시. 추정 관측값이며 현재 접속 기기 수나 계약상 허용 대수로 취급하지 않음 |
| 허용 최대 기기 수 | Outline 공개 관리 API에 기기 수 강제 제한 기능이 없으므로 미지원. 추후 정책값을 저장해도 실제 차단 기능처럼 표시하지 않음 |
| 상태 | 서버에 키 존재, 고객 구독 상태, 조회 상태를 구분. 키가 있다고 현재 접속 중이라고 표시하지 않음 |

설치된 서버 버전과 실험적 metrics 지원 여부는 읽기 조회로 확인한다. 미지원·실패는 빈값/지원 안 함으로 표시하고 0으로 만들지 않는다.

## 작업 흐름

1. 조회 화면과 지표 연동을 먼저 구현하고 모의 테스트한다. 서버의 metrics 공유 설정 등은 임의로 변경하지 않는다.
2. 로컬 PostgreSQL에 실제 서버/키 메타데이터, 사용량 관측, 작업/감사 기록용 독립 테이블을 설계한다. 기존 .test 가상 서버·가상 고객 제약을 풀거나 실제 키를 자동 연결하지 않는다. 마이그레이션 파일과 백업/복원 계획을 검토한 후 승인받아 적용한다.
3. 생성: 서버·키 이름·고객 연결 선택 → 생성 확인 → API 호출 → 생성 결과 검증 및 감사 기록. 비밀 액세스 키는 목록·로그에서 제외하고 권한을 확인한 별도 보기/복사에서만 제공한다. 중복 클릭은 작업 ID/잠금으로 차단한다. 생성 응답 시간 초과는 성공 여부 불명으로 보존하고 자동 재발급하지 않는다.
4. 삭제: 서버·키 ID·연결 고객·이용 상태와 영향을 먼저 표시 → 키 ID 입력 확인 → API 호출 → 서버 목록에서 제거 확인 → 삭제 이력 보관. 활성 고객 키는 경고하고 별도 확인을 요구한다. 삭제 실패/응답 불명은 미확인으로 보존하며 성공으로 표시하거나 자동 재전송하지 않는다. 같은 키 자동 복구를 약속하지 않는다.
5. 실제 쓰기 기능은 별도 서버 측 스위치로 기본 비활성화한다. 구현 승인과 실제 테스트 키 생성·삭제 승인은 분리하며, 실제 검증은 전용 키로만 승인 후 수행한다. IP 교체 스위치와도 분리한다.

## DB 및 이관

서버 식별은 계정·리전·인스턴스·Outline 서버 식별자를 고려한다. 재설치 시 같은 키 ID가 재사용돼도 과거 키에 잘못 연결되지 않도록 서버 세대를 구분한다. 서버/세대/Outline 키 ID의 유일성, 고객 1:1 연결 제약을 검토한다. 실제 고객 데이터와 가상 고객 데이터를 자동 혼합하지 않는다.

운영 메타데이터·작업 기록은 PostgreSQL 백업/복원으로 서버에 이관할 수 있게 한다. Outline 관리 비밀은 현재 DPAPI 저장소와 분리하며 이관 대상 서버에서 재등록한다. 접속 키 비밀을 보존해야 할 경우 별도 암호화·접근 정책을 설계하고 평문 DB/로그/MD에는 넣지 않는다.

## 검증 및 완료 기준

인증·CSRF·서버 대상 검증, 미지원 metrics, API 부분 실패, 날짜 출처, 카운터 리셋, 고객 키 중복 연결, 재설치 후 ID 재사용, 생성 중복/응답 불명, 삭제 실패/동시 실행, 비밀 응답/로그 노출 방지를 검증한다. 실제 키 쓰기는 모의 API로 우선 검증하고 운영 승인을 따로 받는다. 각 단계 완료와 변경사항을 작업현황·관련 MD에 기록하며 GitHub에는 별도 요청 전 반영하지 않는다.

공식 근거: [Outline API 명세](https://github.com/OutlineFoundation/outline-server/blob/master/src/shadowbox/server/api.yml). 키 CRUD·사용량 한도와 실험적 지표를 제공하지만 키별 생성일·활성화일·기기 수 강제 제한은 공개 명세에 없다. 실제 설치 버전에서 지원하는지 별도 확인이 필요하다.
