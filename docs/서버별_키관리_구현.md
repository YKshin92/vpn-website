## 사용 경로

[서버 키 관리](http://127.0.0.1:3000/admin/keys?server=vpnServer001) 또는 기존 관리자 → 서버관리 → 서버 상세 → 키 → 전체 키 관리로 이동한다. 기존 관리자 로그인 세션을 사용한다. 별도 외부 배포는 하지 않았다.

## 화면과 조회

- 서버 선택, 이름/도메인/공개 IP/버전/기본 포트/서버 기본 데이터 한도.
- 전체 키 수, 조회된 사용량 합계, 한도 적용 키 수. 고객 연결은 미연동으로 구분.
- 키 이름/ID 검색, 사용량·개별/서버 기본 한도·잔여량·최근 사용 시각 목록.
- 우측 상세에서 포트, 생성일, 최근 사용과 최근 24시간 최대 관측 기기 수/관측 시각 확인.
- 키 생성·이름 변경·데이터 한도 설정/해제·삭제·접속 키 보기/복사 화면과 확인 창.
- 서버별 최근 100개 관리자 작업 이력. 새 시스템에서 생성한 키의 생성일은 전체 생성 성공 기록에서 서버 식별자와 키 ID를 함께 조회한다.

수치 출처는 Outline API다. `/metrics/transfer`의 집계값을 월간 사용량으로 단정하지 않는다. 미지원·조회 실패·응답 누락은 0으로 바꾸지 않는다. 개별 한도를 해제하면 서버 기본 한도가 적용될 수 있다. 기본 한도를 조회하지 못했으면 무제한이 아닌 조회 불가로 표시한다.

기존 키의 원래 생성일, 최초 활성화일, 고객 구독 시작일은 추정하지 않는다. 고객/요금제 연결과 이용기간은 후속 작업이다. 최대 관측 기기는 실험적 API 값이며 정확한 현재 기기 목록이나 허용 대수 강제 제한을 의미하지 않는다. 기기 수 제한 자체는 제공하지 않는다.

## API·작업 보호

새 API:

- GET `/api/admin/outline/servers`
- GET `/api/admin/servers/:instance/outline/overview`
- POST `/api/admin/servers/:instance/outline/commands`
- POST `/api/admin/servers/:instance/outline/reveal`

등록 서버·AWS 계정/실행 상태/공개 IP를 확인하고 기존 인증서 고정 검증 통신을 재사용한다. 관리 비밀·액세스 키는 목록/일반 결과/오류/작업 기록에 포함하지 않는다. 액세스 키 표시는 별도 확인 요청에서만 허용하며 서버 전환·상세 닫기·로그아웃·페이지 숨김 시 지운다. 복사한 클립보드는 별도이며 자동 삭제를 보장하지 않는다.

실제 쓰기는 `IEUM_OUTLINE_WRITES_ENABLED=true`, 작업 DB 준비, 현재 Outline 서버 식별자 일치, 대상 서버명 확인·동의가 모두 충족돼야 한다. 삭제는 키 ID 재입력도 서버에서 검증한다. 읽기 전용 시작 스크립트는 IP 변경과 키 변경 스위치를 모두 false로 강제한다.

생성은 미리 지정한 무작위 `ieum-UUID` ID로 PUT한다. 작업 ID별 중복 요청은 영속 기록으로 구분하고 서버별 열린 작업을 하나로 제한한다. 먼저 intent를 DB에 커밋한 뒤 변경 API를 한 번 호출하고 키 목록/설정과 서버 식별자를 다시 읽어 검증한다. 중간 실패·응답 불명·마지막 기록 실패는 intent 또는 needs_review를 남기고 이후 작업을 막는다. 자동 재전송·키 복구·추가 생성은 하지 않는다. 중단 작업의 수동 대조/해제 UI는 아직 없으므로 실제 쓰기 시험 전 해당 상황의 운영 절차를 검토해야 한다.

접속 키 보기 역시 별도 reveal 작업으로 감사 기록을 남기고 실제 변경 스위치/작업 DB 준비 전에는 차단한다. 작업 이력은 현재 서버 선택에 연결되며 키 ID가 같아도 서버 재설치 후 serverId가 바뀌면 생성일을 잘못 이어 붙이지 않는다.

## DB·이관과 승인 경계

`backend/migrations/006_outline_key_operations.sql`을 작성했지만 **적용하지 않았다**. 독립 작업 테이블·작업자·서버 식별자·키 ID·의도/완료/확인 필요 상태·시각·감사 인덱스를 준비했다. 실제 개인/키 비밀은 넣지 않는다. 기존 가상 서버/고객 테이블을 수정하거나 실제 고객에 자동 연결하지 않는다.

새 DB 구조는 2026-10-18 명시적 승인 후 기존 백업 포함 migrate 절차로 적용했고 영속/복원 검증도 완료했다. 이관은 PostgreSQL 덤프/복원 대상에 포함되며, 관리 비밀 DPAPI 파일은 다른 OS/사용자로 복사해 사용할 수 없으므로 서버 측 비밀 저장소에 재등록한다. 사용량 시계열 저장·월별 사용량 원장·고객 매핑은 이번 구현 범위가 아니다.

## 검증 결과

- TypeScript 빌드 통과.
- 단위/컨트롤러 90개 통과. 키 CRUD·한도 해제·검증·중복 요청·쓰기 실패·DB 기록 실패·사설 IP/다른 서버 세대 차단·미지원 지표·한도 조회 실패·비밀 값 제외/정리 포함.
- 로컬 PostgreSQL 통합 50개 중 49개 통과, 1개는 기존 관리자 보존으로 생략. 새 화면/자산·인증/CSRF/스키마 검증·비활성 쓰기 API 포함.
- 새 DB DDL을 실제 적용한 검증은 하지 않았으며 journal 영속 쓰기/복원은 적용 후 별도 검증 대상이다. 제어 흐름의 작업 기록은 모의 저장소로 검증했다.
- 실제 HTTP: 새 페이지와 JS/CSS 200, 비로그인 API 401, vpnServer001 키 1개·서버 버전 1.12.3·전송량/실험적 지표 ok 확인. 일반 응답에 password/accessUrl/관리 비밀이 없는 것 확인.
- 실제 `writesEnabled=false`, `journalReady=false`, 변경 요청은 쓰기 차단 403. `to_regclass`로 새 작업 테이블 미적용 확인. 초기 진단에서 앱 DB 계정의 migration 장부 조회 권한 제한을 확인해 권한을 늘리지 않고 테이블 존재 조회로 검증했다.
- 실제 키 생성·이름/한도 변경·삭제·비밀 키 표시·IP/DNS 변경은 실행하지 않았다. 임시 진단 관리자 계정은 정리했다. GitHub 반영 없음.
- 브라우저 접근 정책 제한으로 실제 클릭·스크린샷/시각 검증은 미실행이다. DOM 컨트롤러/소스/HTTP 검증과 구분한다.
